# 01 初回セットアップ（brief.md・entities.csv・prompts.csv）

作業フォルダの `ai-search/` に、観測の土台になる3つのファイルを用意する手順。SKILL.md の「初回セットアップ」を詳しくしたもので、流れはそれと同じである。

3つのうち、判定の結果を直接左右するのは entities.csv である。normalize_observations.py は、ここに書いた表記とドメインだけで言及と引用を判定する。書き漏らした表記は「言及なし」に、一般の語と同じ表記は誤った「言及あり」になる。brief.md の正しい事実の一覧は、回答の正誤を判定する基準になる。prompts.csv はここではファイルを置くだけにし、何を尋ねるかは [02-prompt-set.md](02-prompt-set.md) で決める。

## 1. 目的

- 自社と競合の表記ゆれ・除外語・ドメインを entities.csv にまとめ、言及と引用の数え漏れと数えすぎを防ぐ。
- 回答の正誤を判定する基準として、正しい事実の一覧を出典と確認日付きで brief.md に書く（鉄則7）。
- 観測の条件（サービス、ログイン状態、地域、繰り返しの回数）を最初に決め、ラウンドごとに条件が変わらないようにする（鉄則3）。
- 事業と目標を brief.md に書き、施策を目標に結びつけられるようにする（鉄則6）。seo-operator の `seo/site-brief.md` があれば、同じことを二重に書かない。

## 2. 必要な入力データ

| データ | 入手元（ツール → 画面 → 操作） | 必須/任意 | ないときの動き方 |
|---|---|---|---|
| 自社の正式名・略称・英字表記・カナ表記・旧社名 | ユーザーへの質問。登記上の商号と変更履歴は、国税庁の法人番号公表サイト（`https://www.houjin-bangou.nta.go.jp/`）で法人名を検索し、詳細の画面で確かめる。名称・所在地の変更履歴が公表され、フリガナと英語表記は法人が登記や登録をした場合だけ載る（`https://www.houjin-bangou.nta.go.jp/setsumei/`、2026-09-26 に確認） | 必須 | 聞けた表記だけで始め、1ラウンド目の回答で見つかった表記を足す。正式名がわからなければ `[要追加: 登記上の商号]` を残す |
| 商品名・サービス名・代表者名 | ユーザーへの質問、公式サイトの商品一覧と会社概要 | 任意 | 会社名の行だけで始める |
| 自社のドメイン（旧ドメイン、EC・採用などの別ドメイン） | ユーザーへの質問、公式サイトのフッターとリンク先 | 必須 | 公式サイトのドメインだけで始め、`[要確認: ほかに使っているドメイン]` を残す |

| 競合の候補 | `seo/site-brief.md` の事業上の競合、ユーザーへの質問。1ラウンド目のあとは、回答の本文と compare_runs.py の集計 | 任意（最初は0社でもよい） | 自社の行だけで1ラウンド目を行い、回答に出た企業から選ぶ |
| 正しい事実と出典 | 公式サイト（会社概要、料金、商品一覧、店舗・対応地域）、社内資料、法人番号公表サイト | 回答の正誤を判定するなら必須 | 埋まらない項目は `[要追加: ○○]` のまま残す。一覧にない事実を含む回答の正誤は「未確認」のままにする |
| `seo/site-brief.md` | 作業フォルダの `seo/`（seo-operator の初回セットアップで作るファイル） | 任意 | 事業と目標を brief.md に直接書く（下の質問リストの第2回の5問目） |
| 観測の条件 | ユーザーへの質問 | 必須 | new_round.py の既定（画面 web、ログインなし、地域 JP、言語 ja、各3回）を示し、確認を取る。ただしログインの状態は、サービスごとに [03-observation.md](03-observation.md) の既定の案に従う（claude と copilot は `あり（記憶オフ）`）。サービスは既定がないので必ず聞く |

## 3. 手順

1. 既存のファイルを確認する。作業フォルダの `ai-search/brief.md`・`entities.csv`・`prompts.csv` と、`seo/site-brief.md` を探す（ユーザーが別の場所を指定していればそこ）。
   - 3つともある: 読み込み、brief.md の `最終更新日` を見る。entities.csv を直す依頼なら、下の「entities.csv を直すタイミング」を先に読む。
   - 一部だけある: ないファイルだけを手順2でコピーする。
   - `ai-search/` がない: 作ってよいかをユーザーに確かめる。セットアップを頼まれていない普通の相談では、フォルダを作らずに暫定の回答とセットアップの提案にとどめる。
2. テンプレートをコピーする。スキルフォルダの中のテンプレートは編集しない（クラウドセッションや Cowork では読み取り専用のことがあり、サイト固有の情報をスキルに混ぜないため）。既存のファイルは上書きしない。
   ```bash
   mkdir -p ai-search
   cp -n <スキルのディレクトリ>/templates/brief.md ai-search/brief.md
   cp -n <スキルのディレクトリ>/templates/entities.csv ai-search/entities.csv
   cp -n <スキルのディレクトリ>/templates/prompts.csv ai-search/prompts.csv
   ```
   - テンプレートの CSV には架空の例の行（架空珈琲、サンプル焙煎など）が入っている。自社の値に書き換えるか、行ごと消す。残すと架空の競合を数え続ける。
   - CSV は BOM なしの UTF-8 で置いてある。Excel で直接開くと日本語が文字化けすることがあるので、テキストエディタで直すのが確実。Excel で保存し直して Shift_JIS（cp932）や BOM 付きになっても、スクリプトは読める。
   - 作業フォルダを Git で管理しているなら、brief.md の社外秘の値（未公開の料金など）をコミットしてよいか確かめる。
3. 記入の方法を選んでもらう。
   - A: ユーザーが自分で記入し、終わったら知らせてもらう。Claude が読み、空欄と矛盾、登録しないほうがよい表記を指摘する。
   - B: Claude が質問して埋める。公式サイトがあれば先に下書きを作り（手順5と8）、質問を減らす。1回の質問は5問以内にし、下の質問リストの順に聞く。
4. `seo/site-brief.md` があれば読み、使える欄を下書きに移す（下の「seo/site-brief.md がある場合の読み方」）。
5. 自社の表記ゆれを集め、entities.csv の own の行を書く（下の「表記ゆれの集め方」）。会社名、商品・サービス名、代表者名は別々の行にしてよい。どれが言及されたかが own_entities_mentioned の列でわかる。
6. ドメインと除外語を書く（下の「ドメインの書き方」「除外語の決め方」）。
7. 競合を仮に決め、1ラウンド目のあとで見直す（下の「競合の選び方」）。
8. brief.md の正しい事実の一覧を作る（下の「正しい事実の一覧の作り方」）。
9. brief.md に観測の条件を書く。
   - 観測する組（service・surface・login・mode・region・language）を表にする。最初は2サービスから始める（規模の目安は [02-prompt-set.md](02-prompt-set.md)）。login と mode は、[03-observation.md](03-observation.md) の「サービスごとの観測条件」にある既定の案から選ぶ。login の案はサービスによって違い、chatgpt・gemini・google-ai-mode・google-aio は `なし`、claude と copilot は `あり（記憶オフ）` である（gemini は、ログインなしで使えなければ `あり（記憶オフ）`）。
   - 繰り返しの回数、1ラウンドを何日に分けるか、ラウンドの間隔、ラウンド名の付け方（開始日の `YYYY-MM-DD`）、観測する場所（ネットワーク。VPN は使わない）を決める。サービスごとの条件のそろえ方（記憶やパーソナライズのオフ、検索モード）は 03 にある。
   - brief.md の「最初の観測で確かめたこと」「出典として写すもの・写さないもの」と、1件の記録にかかった時間は、この時点では空でよい。「最初の観測で確かめたこと」は1ラウンド目の前に画面を見て書き、出典の扱いと記録の時間は1ラウンド目で決めて書く（03）。
   - Perplexity の利用規約は 5.2(i) で、自動の手段による監視・抽出・コピー・収集に加え、同じことを手作業で行うことも禁じている（`https://www.perplexity.ai/hub/legal/terms-of-service`、2026-09-26 に確認）。手動の観測でも規約に触れるおそれがあるので、対象に入れるかはユーザーが規約を読んで決める（`[要確認: Perplexity の利用規約 5.2 と、観測の目的・方法の関係]`）。対象にしなかったサービスは、理由と一緒に brief.md に書く。
10. prompts.csv を用意する。この時点では列の決まりだけを確かめ、中身は [02-prompt-set.md](02-prompt-set.md) の手順で作る。
    - prompt_id は英数字で始め、英数字・ハイフン・下線だけにする（例: `P001`）。一度使ったプロンプトの文は直さない。言い回しを変えるときは新しい ID にする。
    - stage は `認知` / `比較` / `購入` / `サポート`、branded は `指名` / `非指名`、active は `yes` / `no`、source は `GSC` / `問い合わせ` / `Bing` / `営業` / `サジェスト` / `その他` のどれか。
11. 仕上げる。brief.md の `最終更新日` と更新履歴を書き、残った `[要確認]` と `[要追加]` を一覧にして渡す（出力フォーマット）。
    - entities.csv の書式の誤りは、normalize_observations.py を初めて実行したときに理由付きで示され、処理が止まる（終了コード 2）。止まるのは、kind の値の誤り、entity_id の重複、`https://` やパスを含むドメイン、自社と競合に同じドメインを書いたとき、などである。
12. 1ラウンド目のあとで entities.csv を見直す（下の「1ラウンド目のあとの見直し」）。

### seo/site-brief.md がある場合の読み方

seo-operator を使っているサイトでは、事業と CV の定義は `seo/site-brief.md` にある。brief.md には写さず、「seo/site-brief.md を参照（最終更新日 {日付}）」と書いて、AI 検索に固有のことだけを足す。seo-operator が入っていない環境や、site-brief がない場合は、この節を飛ばして brief.md に直接書く。

| site-brief の欄 | 使い道 | 扱い |
|---|---|---|
| 基本情報の「ブランド名の表記」 | entities.csv の own の terms の候補 | Search Console でブランド名のクエリを分けるための一覧で、中黒や空白の違いまで書かれているとは限らない。下の「表記ゆれの集め方」で足す |
| 基本情報の「URL」 | domains の候補 | サブドメインや別ドメインの運営サイトも拾う |
| 事業とCV | brief.md の「事業と目標」 | 写さずに参照する。AI 検索で起きてほしいことと、それがどの CV につながるかだけを足す |
| ターゲット | プロンプトの候補 | [02-prompt-set.md](02-prompt-set.md) で使う |
| 商材・強み | 正しい事実の一覧の候補 | 料金や商品の一覧など、出典のある事実だけを移す。「強み」は主張であり正誤を判定できないので、事実の一覧に入れない |
| 主要ページ | 事実の出典、AI に引用されてほしいページ | brief.md の「引用されてほしいページ」に移す |
| 競合の「事業上の競合」 | competitor の候補 | 「検索上の競合」に並ぶ Q&A サイトや比較メディアは競合にしない（下の「競合の選び方」） |
| 制約 | プロンプトや事実の一覧に書けない情報 | 社外秘の情報を AI へのプロンプトに入れない |
| 利用できるデータとツール | Search Console が使えるか | 使えるなら、クエリをプロンプトの候補にできる（02） |

- site-brief に `[要確認]` や `[要追加]` が付いた値は、同じ印を付けたまま使う。確定した値として扱わない。
- site-brief の `最終更新日` が古ければ見直しを提案する（seo-operator は6か月を見直しの目安にしている）。社名や料金が変わっているのに site-brief が古いままだと、事実の一覧も古くなる。

### 表記ゆれの集め方

normalize_observations.py は、照合の前に回答と表記の両方を同じ規則でそろえる。そろう違いは書き分けなくてよい。そろわない違いは、1つずつ terms に書く。

| 違いの種類 | 例（架空） | 扱い |
|---|---|---|
| 全角と半角（英数字・カタカナ） | ＫＡＫＵＵ / KAKUU、ｶｸｳ / カクウ | 自動でそろう |
| 大文字と小文字 | KAKUU COFFEE / Kakuu Coffee | 自動でそろう |
| ダッシュ類 | Kakuu‐Coffee / Kakuu–Coffee / kakuu-coffee | 自動で `-` にそろう |
| 連続する空白、全角の空白 | `kakuu　coffee` / `kakuu  coffee` | 自動で半角の空白1つにそろう |
| 空白の有無、ハイフンと空白 | kakuu coffee / kakuucoffee / kakuu-coffee、架空 珈琲 / 架空珈琲 | そろわない。すべて書く |
| 中黒の有無 | カクウ・コーヒー / カクウコーヒー / カクウ コーヒー | そろわない。すべて書く |
| 漢字・ひらがな・カタカナ | 架空珈琲 / 架空コーヒー / かくうコーヒー / カクウコーヒー | そろわない。すべて書く |
| 長音やローマ字の揺れ | コーヒー / コーヒ、kakuu / kaku / kakū | そろわない。実際に見かけた表記だけを書く |
| 旧字体・異体字 | 髙 / 高、﨑 / 崎 | そろわない。代表者名で起きやすい |
| 法人格 | 株式会社架空珈琲 / 架空珈琲株式会社 / (株)架空珈琲 / Kakuu Coffee Co., Ltd. | 法人格を外した形で書けば、どれにも一致する。法人格付きの形だけを書くと、法人格のない言及を取りこぼす |

集める順番:

1. 公式の表記。登記上の商号（法人番号公表サイト）、会社概要、ロゴ、商品のパッケージに書かれた表記を拾う。
2. 旧社名と旧商品名。法人番号公表サイトの変更履歴と、ユーザーへの質問で拾う。AI の回答は古い情報をもとにすることがあるので、旧社名も terms に入れる。旧社名で書かれた回答は、正誤の判定で「古い情報」の候補になる（[04-citation-gap.md](04-citation-gap.md)）。
3. 商品名・サービス名と代表者名。会社名とは別の own の行にする。代表者名だけが出た回答も「自社の言及」に数えられる。同姓同名の人が多い名前は登録しないか、1ラウンド目のあとで own_mention_snippet を読んで誤検出を確かめる。
4. 実際に使われている表記。Search Console のクエリ、問い合わせ、SNS、レビューで見かける表記を足す。打ち間違いは、何度も見かけるものだけにする。
5. AI の回答での表記。1ラウンド目の回答を読み、まだ登録していない表記を足す（下の「1ラウンド目のあとの見直し」）。

照合の決まりから来る注意:

- 日本語の表記は、前後にどんな文字があっても一致する。「架空」だけを登録すると「架空の話」にも一致するので、2〜3文字の略称や一般の語と同じ表記は、単独で登録しない。登録するなら除外語を添える。
- 英数字で始まる（終わる）表記は、前（後ろ）の文字が英数字なら一致しない。`kakuu` は `kakuu coffee` や `kakuu-coffee` には一致するが、`kakuucoffee` には一致しない。英字の表記は、つなげた形も書く。
- terms は `|` で区切るので、表記の中に `|` は使えない。

### ドメインの書き方

- ホスト名だけを書く（`kakuu-coffee.example`）。`https://` やパスを書くと normalize_observations.py が止まる。先頭の `www.` と末尾の `.` は外して扱われる。
- サブドメイン（`shop.kakuu-coffee.example`）は自動で一致するので、別に書かなくてよい。
- 自社のドメインはすべて書く。旧ドメイン（リダイレクトしていても、AI の出典に旧 URL が出ることはありうる）、EC や採用の別ドメイン、商品のブランドサイトを含める。
- 他社と共有するドメインは書かない。モール、ブログサービス、SNS（`x.com` など）を書くと、同じドメインにある他社のページまで自社の引用として数える。自社専用のサブドメインがあるときだけ、そのサブドメインを書く（例（架空）: `kakuu.shop-platform.example`）。パスで区別されるページ（SNS のアカウント、モールの店舗ページ）は登録できないので、citations.csv の entity_kind が `other` の行から手で拾う。
- 同じドメインを own と competitor の両方に書くと、入力の誤りとして止まる。own の行どうしで同じドメインを共有するのはよい（先の行の entity_id で数えられる）。
- 代表者名の行のようにドメインがない行は、domains を空にしてよい。terms と domains のどちらかがあればよい。

### 除外語の決め方

除外語（exclude_terms）は、登録した表記が一致しても数えない言い回しである。除外語が現れた範囲の中にある一致だけが消える。したがって除外語は、登録した表記を含む、より長い語にする。登録した表記を含まない除外語は何も消さない。

- 例（架空）: 競合の「サンプル焙煎」は、少量を試しに焙煎するという意味の一般の語としても使われうる。「サンプル焙煎機」のように、社名として使われない決まった言い回しを除外語にする。
- 除外語で消せるのは、決まった言い回しだけである。一般の語として使われた場合（「サンプル焙煎で品質を確かめる」）は、文脈で見分けられない。取りこぼし（言及を数えない）と誤検出（言及でないものを数える）のどちらを許すかを決め、決めたことを brief.md の更新履歴に書く。
  - 取りこぼしを許す: その表記を登録せず、英字や店名付きの形（「サンプル焙煎店」）だけを書く。
  - 誤検出を許す: 登録したうえで、ラウンドごとに回答を読んで確かめる。テンプレートの entities.csv の comp-a の行は、こちらの例である。
- 除外語を広く取りすぎない。「架空珈琲の」を除外語にすると、本物の言及まで消える。
- 除外語の候補は、1ラウンド目のあとで見つけるのが確実である。自社の誤検出は observations.csv の own_mention_snippet（最初に一致した箇所の前後20字）で見つかる。競合には同じ列がないので、回答の本文を読んで確かめる。

### 競合の選び方

- 最初は仮に決める。site-brief の事業上の競合や、ユーザーが挙げる「比較されやすい企業」を数社（3〜5社が目安）入れる。0社で始めてもよい。
- 本番の競合は、1ラウンド目で AI が実際に挙げた企業から選ぶ。AI の回答で自社と並べられる相手は、事業上の競合や、検索結果で上位にいるサイトと同じとは限らない。
  - 回答の本文を読んで企業名・サービス名を拾う。entities.csv にない企業は competitors_mentioned に出ないので、スクリプトの出力だけでは見つからない。
  - `python3 <スキルのディレクトリ>/scripts/compare_runs.py --period {ラウンド名}` の集計の末尾に、entities.csv にない出典のホストの上位が出る。引用されている企業の候補になる。
  - 非指名のプロンプトで、複数のプロンプトや複数のサービスにまたがって挙がる企業を優先する。1回だけ挙がった企業は、次のラウンドで様子を見てからでよい。
- 比較メディア、レビューサイト、百科事典、Q&A サイト、公的機関は競合に登録しない。引用される情報源として [04-citation-gap.md](04-citation-gap.md) で扱う。
- 競合の行にも terms と domains を書く。表記ゆれは自社ほど細かくなくてよいが、社名の漢字・カナ・英字は入れる。

### 正しい事実の一覧の作り方

brief.md の「正しい事実の一覧」は、回答が正しいかを判定する基準である。Claude はこの一覧と回答を照らして accuracy を下書きし（reviewed_by は `claude-draft`）、ユーザーが確かめて `human` にする（[03-observation.md](03-observation.md)）。一覧にない値は、回答に書かれていても正しいとみなさない（鉄則7）。

- 項目は、AI に尋ねられそうで、間違えられると困るものを選ぶ。テンプレートの行（正式名、所在地、代表者、料金、対応地域など）から始め、事業に合わせて足し引きする。料金は、税込か税抜かと改定日も書く。
- 「提供していないもの」の行も作る。扱っていない商品、対応していない地域、終了したサービスなど。存在しない商品や機能を AI が説明したときの判定に使う。
- 値ごとに出典と確認日を書く。出典は公式ページの URL か社内資料の名前にする。公開していない事実については、AI が正しく答える材料がない。公開するかどうかは [04-citation-gap.md](04-citation-gap.md) の改善先の検討に回す。
- 値が変わったら、以前の値と変更日を残す。AI が古い値を答えたときに「古い情報」と判定できる。
- 公式ページから読み取った値は出典の URL を添えて書く。ページから推測した値は `[要確認: ○○（根拠: URL）]`、手元にない値は `[要追加: ○○]` にする。記憶や一般論で埋めない。
- 料金や営業時間のように変わりやすい値は、正誤を判定する前に確認日を見る。古ければ公式ページで確かめ直してから判定する。

### entities.csv を直すタイミング

normalize_observations.py は、実行のたびに全ラウンドの回答を今の entities.csv で判定し直す。直せば、過去のラウンドの結果も変わる。実行のたびに書かれる observations.run.json には、entities.csv の SHA-256 が残る。

- 直してよい時期: 1ラウンド目のあと、実験の変更前のラウンドを始める前。この時期に表記ゆれ・除外語・競合を固める。
- 実験の途中で直すと、結果を見てから数え方を変えたことになる。実験の記録に書いた entities_sha256 と、observations.run.json の値が合わなくなる。compare_runs.py は、この食い違いを警告として報告に載せる（[06-experiments.md](06-experiments.md)）。
- どうしても直すなら（誤検出が見つかった場合など）、理由と直した日を実験の記録に書き、判定の報告にも添える。normalize_observations.py は前と後のラウンドをどちらも今の entities.csv で判定し直すので、前後の数え方はそろう。ずれるのは、実験を計画した時点の数え方との関係である。
- 直したら、brief.md の更新履歴に日付と変更内容を書く。

### 1ラウンド目のあとの見直し

1. `python3 <スキルのディレクトリ>/scripts/normalize_observations.py --workspace ai-search` を実行し、observations.csv を作る。
2. own_mentioned が 1 の行の own_mention_snippet を読み、一般の語への一致などの誤検出を探す。見つかったら、除外語を足すか表記を見直す。
3. 回答の本文を読み、登録していない自社の表記と、登録していない企業名を拾う。
4. compare_runs.py の `--period` の集計で、entities.csv にない出典のホストを見る。
5. entities.csv を直し、手順1をもう一度実行して、直した箇所の結果が変わったことを確かめる。

## 6. よくある失敗

- 中黒や空白の違いも自動でそろうと思い込む: そろうのは全角・半角、大文字・小文字、ダッシュ類、連続する空白だけ。「カクウ・コーヒー」と「カクウコーヒー」は両方書く。
- terms に法人格付きの形だけを書く: 「株式会社架空珈琲」だけだと、「架空珈琲」と書かれた回答を取りこぼす。法人格を外した形で書く。
- 短い略称や一般の語を単独で登録する: 日本語の表記は前後の文字を問わず一致するので、「架空」は「架空の話」にも一致する。単独で登録せず、登録するなら除外語を添える。
- 英字の表記を1つの形だけ登録する: `kakuu` は `kakuucoffee` に一致しない。空白あり、つなげた形、ハイフンの形を書く。
- モールや SNS のドメインを domains に書く: 同じドメインの他社のページまで自社の引用として数える。自社専用のサブドメインだけを書く。
- ドメインに `https://` やパスを書く: normalize_observations.py が行番号付きのメッセージを出して止まる。ホスト名だけにする。
- テンプレートの架空の行を残す: 架空の競合を数え続ける。自社の値に書き換えるか消す。
- 最初に決めた競合を固定する: AI が自社と並べる相手は違うことがある。1ラウンド目の回答と、entities.csv にない出典のホストを見て選び直す。
- 比較メディアやレビューサイトを競合に登録する: 競合の言及・引用の件数に情報源が混ざる。情報源は 04-citation-gap.md で扱う。
- 実験の途中で entities.csv を直す: 過去のラウンドの判定も変わり、compare_runs.py が警告を出す。表記ゆれと競合は、実験の変更前のラウンドより前に固める。
- 正しい事実を記憶や一般論で書く、出典と確認日を書かない: 正誤の判定の根拠にならない。公式ページか社内資料を出典にし、なければ `[要追加: ○○]` のまま残す。
- 公式サイトの「強み」を事実の一覧に入れる: 主張は正誤を判定できない。料金や対応地域のような確かめられる値だけを入れる。
- どのサービスもログインなしで観測すると決める: Claude はログインせずに使えるという公式の記述が見つからず、Copilot の使用条件はログインを必須としている（出典と確認日は 03-observation.md の各サービスの節）。ログインの状態は、サービスごとに 03 の既定の案から選ぶ。
- 各サービスの利用規約を読まずに観測の対象を決める: Perplexity の利用規約は、手作業による監視・コピー・収集も禁じている（手順9）。対象に入れるかはユーザーが規約を読んで決め、決めた理由を brief.md に書く。
