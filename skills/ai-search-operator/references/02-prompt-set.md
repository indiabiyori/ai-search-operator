# 02 プロンプトセットの設計

観測で AI に尋ねるプロンプトの集合（プロンプトセット）を作り、`ai-search/prompts.csv` に固定する手順。運用の型（観測だけか実験か）で、要る規模が変わる。

## 1. 目的

- 実際の顧客の質問から、観測に使うプロンプトセットを作り、`ai-search/prompts.csv` に固定する。一度使ったプロンプトの文は直さない。
- 運用の型に合わせて、1ラウンドの記録数を式で見積もってから始める。回らない規模で始めて、未記入の回答を積み上げない。
- 各プロンプトに段階、指名かどうか、意図のまとまり（intent_group）、出どころを付ける。段階別・指名と非指名別の集計と、引用ギャップの分析（[04-citation-gap.md](04-citation-gap.md)）に使える形にするため。
- 実験では、対象プロンプトと対照プロンプトを変更前のラウンドの前に決め、判定に要る数がそろう見込みを確かめる。判定の読み方は [06-experiments.md](06-experiments.md) にある。
- AI で何回尋ねられているか（需要）は推定しない（鉄則1）。Search Console の表示回数や Bing の引用数は、候補を選ぶ参考にとどめる。

## 2. 必要な入力データ

| データ | 入手元（ツール → 画面 → 操作） | 必須/任意 | ないときの動き方 |
|---|---|---|---|

| 自社と競合の名前（表記ゆれ） | `ai-search/entities.csv`（01） | 必須 | 指名・非指名を分けられない。自社の正式名・略称・商品名と、主な競合の名前だけを先に聞く |
| 事業と CV の定義 | seo-operator を使っていれば、作業フォルダの `seo/site-brief.md` | 任意 | brief.md の「事業と目標」で代える |
| Search Console のクエリ | seo-operator を使っていれば、`seo/data/` に置いたクエリ別のファイル（seo-operator の 10-gsc-growth.md の置き方）を読む。なければ Search Console →「検索パフォーマンス」→「検索結果」→ 期間を設定 →「エクスポート」→ ZIP の中のクエリ別のファイル（`クエリ.csv` という名前のことが多い） | 任意（既存のサイトでは推奨） | 公開前・公開直後のサイトにはデータがないので使わない。ほかの出どころだけで作る |
| Bing のグラウンディング クエリ | Bing Webmaster Tools →「AI Performance」→ グラウンディング クエリのタブ（英語の画面では Grounding queries）→ エクスポート（CSV か Excel） | 任意 | サイトを Bing Webmaster Tools に登録していないか、引用が少なくて表示されない。この出どころは使わず、出どころの対応表にその旨を書く |
| 問い合わせ・サポートに届く質問 | 問い合わせフォーム、メール、チャットの履歴。個人情報と社外秘の情報を除き、質問だけを渡してもらう | 推奨 | よく届く質問を5〜10件、思い出せる範囲で挙げてもらう |
| 営業が受ける質問 | 営業担当への聞き取り（商談で比べられる相手、よく聞かれる質問） | 任意 | 使わない |
| サジェスト | Google の検索窓のサジェスト、ラッコキーワードの「よくある質問検索」など（seo-operator の 03-keyword-research.md と同じ入手元） | 任意 | 使わない |
| 既存のプロンプトセット | `ai-search/prompts.csv` | 2回目以降は必須 | 初回は `templates/prompts.csv` を作業フォルダの `ai-search/` にコピーして使う。スキルのフォルダのテンプレートは直接編集しない |
| 既にある観測の結果（実験の対象・対照を選ぶとき） | `ai-search/observations.csv` と、`compare_runs.py --period` の集計（[03-observation.md](03-observation.md)） | 実験では推奨 | 変更前の率がわからないまま対照を選ぶことになる。出力の「変更前の率」を `[要追加: compare_runs.py --period の集計]` にする |

## 3. 手順

1. 運用の型を決める。brief.md の目標を読み、観測だけか実験かを決める。迷ったら観測だけの運用から始める。観測だけのラウンドの結果は、実験の対象と対照を選ぶ材料になる。ただし実験の変更前のラウンドには数えない。実験の条件は変更前のラウンドを始める前に決めて書く決まりで、条件を決める前の回答はそれを満たさないため（06）。
2. 質問を集める。出どころごとに候補を集め、`source` の値を付ける（下の「質問の出どころと、それぞれの偏り」）。
3. 候補を、プロンプトの文に直す（「プロンプトの文は、顧客が AI に打つ形で書く」）。
4. 段階と指名・非指名に分け、件数の表を作って偏りを見る（「段階と指名・非指名の分け方」）。
5. 同じ意図の言い回しを1つの intent_group にまとめ、代表の1文を選ぶ。
6. 1ラウンドの記録数を式で出し、手間が回るかを確かめる（「規模の決め方」）。
7. 実験のときは、対象プロンプトと対照プロンプトを選ぶ（「実験の対象プロンプトは多めに用意し、intent_group を散らす」「対照プロンプトの選び方」）。
8. prompts.csv に書いて ID を振り、ユーザーに確かめてもらってから固定する（「prompts.csv の書き方」）。次は [03-observation.md](03-observation.md) の手順で、new_round.py で回答ファイルのひな形を作る。

### 観測だけの運用と実験の運用では、要る規模が違う

| | 観測だけの運用 | 実験の運用 |
|---|---|---|
| 目的 | 言及率・引用率・誤った説明の率の現状を知り、引用ギャップを探す（04） | 変更の前後を比べ、改善シグナル・悪化シグナル・明確な変化を検出せず・判定不能のどれかを出す（06） |
| サービス | 顧客が使うサービスを選ぶ。組（サービス・画面か API か・ログイン状態・モード・地域・言語）ごとに別々に集計する | 1サービス・1モードに絞り、その組を確認的に判定する組（primary_group）にする |
| プロンプトの選び方 | 段階と指名・非指名を広く覆う | 変更で動きうる対象プロンプトと、動かないはずの対照プロンプト |
| 数の決め方 | 手間が回る範囲で小さく始め、ラウンドごとに足す | 差が出たプロンプトが6件以上になる見込みで決める。見込みが立たなければ、変更の範囲か観測の手間を見直す |
| 途中の変更 | 新しいプロンプトを足してよい（文は直さない） | 対象・対照の集合は変更前のラウンドの前に決め、判定が済むまで変えない |
| 結果の出し方 | 件数（k/n）を出す。判定はしない | compare_runs.py の判定。確認的な判定は事前に決めた1組・1指標だけで、ほかは探索的な判定 |

v1.0.0 では観測だけの運用を主な使い方にする。手動の観測の手間と、判定に要る件数は両立しにくいので、実験は1サービス・1モードに絞れば回せる場合に行う。

### 質問の出どころと、それぞれの偏り

| source の値 | 出どころ | 向いている使い方 | 偏りと注意 |
|---|---|---|---|
| `GSC` | Search Console のクエリ | Google 検索で自社が表示されている話題が、AI の回答でどう扱われるかを見る | Google の検索窓に打たれた短い語で、AI に打つ文とは形が違う。自社が表示された話題に偏る。表示回数は AI で尋ねられる回数ではない |
| `Bing` | Bing のグラウンディング クエリ | Copilot などで自社がすでに引用されている話題を知る | ユーザーの質問そのものではない（下の Bing の説明）。自社が引用された話題に偏る |
| `問い合わせ` | 問い合わせ・サポートに届く質問 | 顧客の言葉をそのまま使える。サポート段階のプロンプトと、誤った説明の確認に向く | 個人情報を除く。既存の顧客の質問に偏る |
| `営業` | 営業が受ける質問 | 比較段階のプロンプト（競合と比べる質問） | 聞き取った記憶に頼るので、元の言い回しを出どころの対応表に残す |
| `サジェスト` | 検索窓のサジェストなど | 認知段階の疑問の言い回しを拾う | 検索の語で、会話の文ではない |
| `その他` | 上のどれにも当たらないもの（担当者の仮説など） | 自社がまだ表示も引用もされていない話題を足す | 仮説であることを出どころの対応表に書く |

`GSC` と `Bing` は、自社がすでに表示・引用されている話題に偏る。引用ギャップを探すなら、問い合わせと営業の質問から、自社がまだ出てこない話題のプロンプトを足す。

Search Console のクエリについて（2026-09-26 に Search Console ヘルプで確認）:

- 生成 AI パフォーマンス レポート（検索）でヘルプに挙がっている分け方（ディメンション）は、ページ・国・日付・デバイスで、クエリはない。Google の AI による概要・AI モードで表示されたクエリはこのレポートからは取れないので、通常の検索パフォーマンスのクエリを使う（[生成 AI パフォーマンス レポート（検索）](https://support.google.com/webmasters/answer/16984139?hl=ja)）。
- 検索パフォーマンスのクエリからは、プライバシーを守るために一部のクエリ（匿名化されたクエリ）が除かれる。内部の制限で、それ以外にも表に出ないクエリがある（[ディメンションとデータのグループ化](https://support.google.com/webmasters/answer/17011259?hl=ja)）。表には1,000行の制限もある（上の生成 AI パフォーマンス レポートのヘルプが、通常のデータ制限として挙げている）。
- ブランドクエリと非ブランドクエリのフィルタがあり、指名・非指名を分ける手がかりになる。ただし表示回数が少ないサイトでは使えず、誤って分類される語もあるとヘルプに書かれている（同じ「ディメンションとデータのグループ化」）。prompts.csv の `branded` は、entities.csv の自社の表記と照らして決める。

Bing のグラウンディング クエリについて（2026-09-26 に [Bing Webmaster Tools のヘルプ「AI Performance」](https://www.bing.com/webmasters/help/ai-performance-9f8e7d6c)で確認）:

- 対象は Microsoft Copilot、Bing の AI による要約、一部の提携先のサービス。
- グラウンディング クエリは、AI が回答で引用したコンテンツを取得したときの語句を、短くまとめて示したもの。ユーザーの質問やプロンプトそのものではない、と書かれている。そのままプロンプトにせず、話題の手がかりとして、プロンプトの文に直す。
- データは引用の活動の抜き取りで、少ない活動は表示されないことがある。引用が少ない期間はグラウンディング クエリが出ないことがあり、それはペナルティや除外を意味しない、とも書かれている。
- グラウンディング クエリの表は、引用数付きで CSV か Excel にエクスポートできる。
- 2026-06-16 の Bing の公式ブログによると、AI Performance に Intents・Topics・Citation Share・Compare の4つの機能がプレビューとして加わった（[New AI Visibility Insights in Bing Webmaster Tools](https://blogs.bing.com/search/2026/6/New-AI-Visibility-Insights-in-Bing-Webmaster-Tools-Intents-Topics-Citation-Share-Compare/)）。このうちプロンプトの候補選びの手がかりになるのは、グラウンディング クエリを意図の種類で分ける Intents と、関連するグラウンディング クエリをテーマでまとめる Topics の2つ。Intents と Topics がエクスポートに含まれるかは確認できていない。4つの機能の読み方は [07-platform-reports.md](07-platform-reports.md) の手順3にある。

seo-operator が入っていない環境では、上の画面から直接エクスポートしてもらう。seo-operator が入っていれば、`seo/data/` にあるクエリ別のファイルと `seo/site-brief.md` を読み、同じデータを二度頼まない。

### プロンプトの文は、顧客が AI に打つ形で書く

- 顧客が AI の入力欄に打ちそうな、完結した日本語の文にする。検索の語の並び（「コーヒー豆 定期便 比較」）は、意図を読み取って文に直す。語の並びのまま尋ねる顧客もいると考えるなら、それは言い回しの揺れとして扱う（「prompts.csv の書き方」）。
- 1つのプロンプトで1つのことを尋ねる。
- 非指名のプロンプトに、自社の名前も競合の名前も入れない。「架空珈琲も含めて」のような誘導もしない。
- 顧客が付けない指示（「出典を付けて」「表にして」）を足さない。回答の形が変わり、顧客が見る回答と別物になる。
- 「今年の」「最新の」のように、尋ねた日で意味が変わる語は実験の対象に使わない。前と後で、同じ文でも尋ねている中身が変わる。
- 個人情報、社外秘の情報、実在の顧客の名前を入れない。
- 回答の正誤を確かめたい指名のプロンプトは、brief.md の正しい事実の一覧の項目（料金、送料、対応地域、解約の方法など）に対応させる。正誤の判定は 03 で、この一覧と照らして行う。

### 段階と指名・非指名の分け方

`stage` は4つから選ぶ。

- 認知: 課題や基礎知識を知りたい
- 比較: 候補を比べて選びたい
- 購入: 買い方、料金、申し込みを知りたい
- サポート: 買った後の使い方、手続き、困りごと

`branded` は、自社の名前（entities.csv の kind が `own` の行の表記）を含めば `指名`、含まなければ `非指名` にする。競合の名前だけを含むプロンプトは `非指名` とし、intent_group で分けて見る。

段階と指名・非指名を掛け合わせると8つの区分になる。例（架空。架空珈琲の場合）:

| 段階 | 指名 | 非指名 |
|---|---|---|
| 認知 | 架空珈琲はどんなお店ですか | 浅煎りと深煎りのコーヒー豆はどう違いますか |
| 比較 | 架空珈琲とサンプル焙煎の定期便はどう違いますか | コーヒー豆の定期便を選ぶときは何を比べればよいですか |
| 購入 | 架空珈琲の定期便の料金はいくらですか | 自家焙煎のコーヒー豆を通販で買える店を教えてください |
| サポート | 架空珈琲の定期便を休むにはどうすればよいですか | 届いたコーヒー豆はどう保存すればよいですか |

8つを同じ数でそろえる必要はない。brief.md の目標に近い段階を厚くする。非指名のプロンプトは、AI が何を挙げ、どの情報源を引用するかを見る中心で、引用ギャップの分析（04）の材料になる。指名のプロンプトは、誤った説明を見つける中心になる。空いた区分は、空いている理由（例: 指名で検索されるほど知られていない）を出力に書く。

### 規模の決め方

1ラウンドの記録数は次の式で決まる。

```text
記録数 = プロンプト数 × サービス数 × 回数
```

- 回数は、同じ条件で繰り返し尋ねる回数。このスキルは3回を基本にし、2日以上に分けて尋ねる（[03-observation.md](03-observation.md)）。compare_runs.py が前後の比較に入れるプロンプトに求める、有効な回答の最小件数（`--min-repeats`）の既定も3である。
- 1ラウンドの手間は「記録数 × 1件の記録にかかる時間」になる。1件の時間はサービスや回答の長さで変わるので、ここでは決め打ちしない。最初のラウンドで測り、brief.md の観測の条件の欄に書いておくと、次の規模を決めやすい。
- 集計は組ごとに分かれ、組をまたいで合算しない。サービスを増やすと記録数は増えるが、1つの組の件数は増えない。
- サービスは、顧客が実際に使うものから選ぶ。AI アシスタントからの流入を GA4 で確かめる方法は [07-platform-reports.md](07-platform-reports.md) にある。このスキルの例では `chatgpt` と `google-ai-mode` を使う。
- Perplexity は使わない。一般向けの画面での観測は、手動でもこのスキルでは非対応にしている。[Perplexity の利用規約](https://www.perplexity.ai/hub/legal/terms-of-service)（日本語版、最終更新日 2026-01-23、2026-09-27 に確認）は、5.1 で利用を個人の非営利目的に限り、5.2(i) でサービスの監視・抽出・コピー・収集を、自動の手段でも手作業でも禁じている（詳しくは [services/perplexity.md](services/perplexity.md)）。

観測だけの運用では、10〜15問・2サービス・各3回から始めるのをこのスキルの目安にする。式に当てはめると、10 × 2 × 3 = 60件から 15 × 2 × 3 = 90件になる。この目安は、手間を抑えて始めるためにこのスキルが決めた大きさで、統計にもとづく値ではない。記録が回ることを確かめてから、ラウンドごとにプロンプトを足す。

実験の運用では、1ラウンドの記録数は「（対象プロンプト数 ＋ 対照プロンプト数）× 1 × 回数」になる。実験全体では、これに変更前と変更後のラウンド数を掛ける。変更前のラウンドは2回以上行う（06）。

### 実験の対象プロンプトは多めに用意し、intent_group を散らす

compare_runs.py の判定の単位はプロンプトである。回答どうしは独立ではない（同じプロンプトの繰り返しを含む）ので、回答の件数ではなくプロンプトの数が判定の力を決める。判定は次の順で絞り込まれる。

1. 前と後の両方の期間にあり、有効な回答の数が前後で同じで、`--min-repeats` 件以上あるプロンプトだけが比較に入る。1件でもエラーや未記入が出ると、そのプロンプトは前後で件数がそろわず外れる。
2. 比較に入ったプロンプトのうち、率が上がったか下がったものだけを数える（この数が m）。率が同じプロンプトは数えない。
3. m が6未満なら判定不能になる。

率が同じになるプロンプトは多くなりやすい。1つの期間の有効な回答が3件なら、率は 0、1/3、2/3、1 の4通りしかない。変化が小さいと、多くのプロンプトは 0 → 0 や 1 → 1 のままになる。指名のプロンプトでは回答に社名が出やすいので、言及率は動きにくい。このため対象プロンプトを10問用意しても、m が6に届かないことがある。何問あれば足りるかは前もっては決まらないので、既にある観測の結果で率が動いているプロンプトの数を見て見積もる。

m が6以上でも、向きがそろっていなければシグナルにならない。判定は両側の正確な符号検定（既定は α = 0.05）で、m が8以下では1件でも逆向きがあるとシグナルにならない。m ごとに逆向きが何件まで許されるかの表は、[06-experiments.md](06-experiments.md) の手順1にある。さらに、実務上の最小効果（min_effect）と対照で調整した差によって、シグナルが「明確な変化を検出せず」や「判定不能」に変わることがある（06）。

対象プロンプトを選ぶときの決まり:

- 変更で動きうるプロンプトに限る。変更したページが答えになりうるものを選ぶ。例（架空）: 料金ページに税込の料金表を載せる変更なら、料金、送料、定期便の値段を尋ねるプロンプト。
- 実験は1サービス・1モードに絞る。手間は記録数に比例するので、同じ手間ならサービスを減らしてプロンプトを増やすほうが、確認的な判定の力は上がる。ほかの組を観測しても、その結果は探索的な判定にとどまる。
- 1つの intent_group に偏らせない。同じ意図の言い回しは互いに似た動きをするので、1つの変化が何件分にも数えられ、シグナルが出やすくなる。1つの intent_group から入れるのは代表の1文を基本にする。
- 変更が答えになる意図が少なく、対象を増やせないときは、言い回しを足して数を水増ししない。判定不能になりうることを先に伝え、観測だけの運用で様子を見る案を並べる。

### 対照プロンプトの選び方

対照プロンプトは、施策の影響とサービス側の変動を見分けるために置く。対象と対照の両方が同じように動いたら、変化は施策ではなくサービス側の変動かもしれない。

- 変更したページが答えにならない話題から選ぶ。例（架空）: 料金ページの変更なら、豆の保存方法や焙煎度の違いを尋ねるプロンプト。
- 段階、指名かどうか、変更前の率、サービスを、対象となるべくそろえる。サービスは実験の組と同じにする（詳しくは 06）。
- 対象と同じ intent_group のプロンプトを対照にしない。変更の影響が対照にも及ぶ。
- 対照にも複数のプロンプトを用意する。対照も前後の比較の条件（前後で同じ件数、`--min-repeats` 件以上）を満たさないと使えない。使える対照が1つもなければ、対象がシグナル（改善シグナルか悪化シグナル）のときに、判定の理由へ「対照がないため、サービス側の変動と区別できない」と書かれる。
- 決めた対象と対照は、変更前のラウンドを始める前に `ai-search/experiments/E001.md` の `target_prompts` と `control_prompts` に書く。new_round.py の `--prompts` で、その ID だけのひな形を作れる。

### prompts.csv の書き方

列は次のとおり。

| 列 | 書き方 |
|---|---|
| prompt_id | 英数字で始まり、英数字・ハイフン・下線だけ。例: `P001` |
| prompt | AI に尋ねる文 |
| stage | `認知` / `比較` / `購入` / `サポート` |
| branded | `指名` / `非指名` |
| intent_group | 同じ意図の言い回しをまとめる名前（任意） |
| source | `GSC` / `問い合わせ` / `Bing` / `営業` / `サジェスト` / `その他` |
| active | `yes` / `no`。`no` の行は new_round.py が使わない |
| added_on | 追加した日 |

例（架空）。`templates/prompts.csv` の4行（P001〜P004）をコピーしたあとに足した2行:

```csv
prompt_id,prompt,stage,branded,intent_group,source,active,added_on
P005,浅煎りのコーヒー豆はどこで買うのがよいですか,購入,非指名,浅煎りの豆の購入,GSC,yes,2026-09-26
P006,鮮度のよいコーヒー豆の通販の店はどう見分ければよいですか,比較,非指名,鮮度で店を選ぶ,営業,yes,2026-09-26
```

- 一度観測に使ったプロンプトの文は直さない。前と後で尋ねている中身が変わり、比べられなくなる。直したいときは新しい ID で行を足し、古い行の `active` を `no` にする。normalize_observations.py は回答ファイルの `prompt` の欄と prompts.csv の文を比べ、違っていれば警告を出す。
- 行を消さない。ID は最後の行の続きから振り、使い回さない。過去の回答ファイルがその ID で段階や指名・非指名と結びついており、prompts.csv にない ID は警告になる。
- 言い回しの揺れは、代表の1文だけを `active=yes` にして観測する。揺れの影響を見たいときだけ、同じ intent_group に別の ID で数問を足して小さく試す。実験の対象には入れない。
- 観測だけの運用では、ラウンドの間にプロンプトを足してよい。期間によってプロンプトの顔ぶれが違うと率を単純に比べられないので、compare_runs.py の前後の比較は、両方の期間にあるプロンプトだけを使う。実験の途中で足したプロンプトも、片方の期間にしかないので、その実験の判定には入らない。

固定したら、1ラウンド目のひな形を作る（手順の続きは [03-observation.md](03-observation.md)）。

```bash
python3 <スキルのディレクトリ>/scripts/new_round.py --round 2026-10-01 --services chatgpt,google-ai-mode --repeats 3 --mode 検索あり
```

new_round.py は、作ったファイルの数と、1ラウンドの記録数（プロンプト数 × サービス数 × 回数）を表示する。見積もりと合っているかを確かめる。

`--mode` の値は、1回の実行で作るすべてのファイルの `mode` に入る。上の2つのサービスは、03 の「サービスごとの既定の案」でどちらも `検索あり` なので、まとめて作れる。`mode` の書き方がサービスで違うときは、サービスごとに分けて実行する。値に `/` は使えない。付けなければ `mode` は空のまま作られるので、回答を貼るときに書く。

## 6. よくある失敗

- 規模を決めずに、全部のサービスで全部のプロンプトを尋ね始める: 記録数は掛け算で増える。途中で記録が止まると未記入が増え、前後で件数がそろわずに比較から外れる。式で記録数を出してから始める。
- Search Console の表示回数を AI での需要とみなす: 表示回数は Google 検索での数で、AI で尋ねられる回数ではない。プロンプトの重み付けや「AI で月に何回聞かれている」の推定に使わない（鉄則1）。
- グラウンディング クエリをそのままプロンプトにする: Bing はユーザーの質問やプロンプトそのものではないと説明している。話題の手がかりとしてプロンプトの文に直し、`source` を `Bing` にする。
- 自社が出ている話題のプロンプトだけを集める: Search Console と Bing のデータは、自社がすでに表示・引用されている話題に偏る。問い合わせと営業の質問から、自社がまだ出てこない話題のプロンプトを足す。
- 非指名のプロンプトに社名を入れる、または誘導する: 言及率が実際より高く出る。社名を含むプロンプトは指名に分ける。
- 観測に使ったプロンプトの文を直す: 前と後で尋ねている中身が変わる。新しい ID で足し、古い行を `active=no` にする。
- 実験で、同じ意図の言い回しを並べて対象の数を増やす: 似た動きをするプロンプトが何件分にも数えられ、シグナルが出やすくなる。1つの intent_group からは代表の1文を基本にする。
- 実験で、複数のサービス・モードの結果から都合のよい組を選ぶ: 確認的な判定は、事前に決めた primary_group の1組・1指標だけ。ほかの組は探索的な判定として書く。
- 対照を置かない、または対象と同じ intent_group のプロンプトを対照にする: サービス側の変動と施策の影響を区別できない。
- 変更前のラウンドを始めてから、対象と対照を入れ替える: 結果を見て条件を選んだことになる。入れ替えるなら実験をやり直す。
- プロンプトの言い回しごとにページを作る: プロンプトセットは観測のためのもので、ページを量産する計画ではない。言い回しごとのページの量産は操作を目的とした施策に当たる（鉄則5、[00-principles.md](00-principles.md)）。
- 個人情報や社外秘の情報をプロンプトに入れる: 問い合わせの文をそのまま使うときに起きやすい。質問の部分だけを残す。
