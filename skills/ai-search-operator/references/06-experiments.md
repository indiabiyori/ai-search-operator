# 06 改善実験の設計と判定

施策の前後で AI の回答がどう変わったかを、観測ログから決まった規則で判定するための手順。実験の記録（`ai-search/experiments/E001.md`）の書き方、変更前に決めること、対象プロンプトと対照プロンプトの選び方、`compare_runs.py --experiment` の判定と報告の読み方を扱う。

実験の判定には、1つのサービス・1つのモードに絞って、同じ条件の観測を変更の前後で同じ回数だけ続ける手間がかかる。現状の把握と引用ギャップの分析だけなら、この手順は要らない（[03-observation.md](03-observation.md)、[04-citation-gap.md](04-citation-gap.md)）。

## 1. 目的

- 施策の前後の変化を、件数に基づく決まった規則（改善シグナル・悪化シグナル・明確な変化を検出せず・判定不能）で判定する（鉄則1・2）。
- 判定の条件を、結果を見る前に決めて記録する。結果に合わせて条件を動かさない。
- 改善シグナルを施策の効果と言い切らない。明確な変化を検出せず・判定不能も結果として残し、次の実験の設計に使う。
- 実験する施策は、brief.md の事業の目標につながるものに限る（鉄則6）。

## 2. 必要な入力データ

| データ | 入手元（ツール → 画面 → 操作） | 必須/任意 | ないときの動き方 |
|---|---|---|---|
| 観測ログ（`observations.csv` と `observations.run.json`） | 回答ファイルを貼り付けたあと、`normalize_observations.py` を実行して作る（[03-observation.md](03-observation.md)） | 必須 | 率も判定も出さない。何をどう記録するかを 03 で示す |
| プロンプトセット（`prompts.csv`） | 作業フォルダの `ai-search/prompts.csv`（[02-prompt-set.md](02-prompt-set.md)）。stage・branded・intent_group の列を対象と対照の選択に使う | 必須 | 02 の手順で先に作る |
| 試す施策と、その根拠 | 引用ギャップ・誤った説明の分析（[04-citation-gap.md](04-citation-gap.md)）。どのプロンプトのどの回答で、何が足りなかったか | 必須 | 根拠のない施策は実験にしない。先に 04 の分析を行う |
| 本番に反映した日 | CMS の公開履歴、デプロイの記録、作業した人への確認 | 必須 | 反映日がわからない変更は、確認的な判定に使わない。探索的な比較にとどめる |
| 変更前の率（対象と対照を選ぶための材料） | 観測だけの運用で記録した直近のラウンドを `compare_runs.py --period` で集計する | 任意 | 観測の記録がまだなければ、段階と指名・非指名だけで対照を選び、率をそろえられなかったと記録に書く |
| 期間中の出来事 | 自社の記録（同じページへの別の変更、プレスリリース、キャンペーン）と、各サービスの更新の告知 | 任意 | 実験の記録の「期間中に起きたこと」に「不明」と書く |
| 生成 AI パフォーマンス レポート（Google の AI 機能を扱う実験のとき） | Search Console の画面で読む（[07-platform-reports.md](07-platform-reports.md)） | 任意 | 観測ログだけで判定する。レポートは判定に混ぜず、参考として並べる |

## 3. 手順

### 手順1 実験にするかを決める

次の3つがそろえば実験にする。そろわなければ、観測だけの運用を続けながら `--before` と `--after` で探索的に比べる（結果はすべて探索的と書く）。

1. 試す施策が1つの分類に絞れている（コンテンツ / エンティティ / クローラー / 外部の言及 / 技術）。
2. 確認的に判定する1つの組（サービス・画面か API か・ログイン状態・モード・地域・言語）で、変更の前と後に同じ数のラウンドを、同じ繰り返しの回数で観測できる。
3. 対象プロンプトを十分に用意できる（下の表）。

判定は符号検定で行う。差が出たプロンプト（上がった＋下がった）の数を m とすると、α = 0.05 で改善シグナル（または悪化シグナル）になるには、逆向きのプロンプトが次の件数以下でなければならない。値は compare_runs.py と同じ式（両側の正確な符号検定）で計算した。

| 差が出たプロンプトの数 m | 逆向きが許される件数 |
|---|---|
| 5 以下 | 判定不能（m が6未満） |
| 6〜8 | 0（すべて同じ向き） |
| 9〜11 | 1 |
| 12〜14 | 2 |
| 15〜16 | 3 |
| 17〜19 | 4 |
| 20 | 5 |

- 率が前後で同じだったプロンプトは m に入らない。10問を対象にしても、2問で率が変わらなければ m は 8 で、8問すべてが同じ向きでなければシグナルにならない。
- 同じ率になりやすいのは、繰り返しが少ないときと、率が 0 や 1 に張り付いているときである。1プロンプト3回だけなら率は 0、1/3、2/3、1 の4段階しかない。前後の期間をそれぞれ2ラウンドにすると、1プロンプトあたり6件になり、段階が細かくなる。
- 1ラウンドの記録数は、プロンプト数 × サービス数 × 回数になる。例（架空）: 対象10問と対照6問を1サービスで各3回尋ねると、1ラウンド48件。前後2ラウンドずつなら192件を記録する。
- 符号検定は、プロンプトどうしが互いに独立に動くとみなしている。同じ intent_group の言い回しは似た動きをするので、対象を1つの intent_group に偏らせない（[02-prompt-set.md](02-prompt-set.md)）。

### 手順2 実験の記録を作り、変更前のラウンドの前に条件を決める

テンプレートを作業フォルダにコピーする。ID は E001、E002 のように通し番号にし、ファイル名と先頭の id の欄をそろえる。同じ名前の記録が既にあれば、上書きせずに残す（[01-setup.md](01-setup.md) の手順2と同じ書き方）。

```bash
mkdir -p ai-search/experiments
[ -e ai-search/experiments/E001.md ] || cp <スキルのディレクトリ>/templates/experiment.md ai-search/experiments/E001.md
```

先頭の欄は compare_runs.py が読む。欄の意味と書く時期は次のとおり。

| 欄 | 意味 | 書く時期 | 例（架空） |
|---|---|---|---|
| id | 実験の ID | 作ったとき | `E001` |
| status | `計画中`（条件を決めている）/ `実施中`（変更前のラウンドを始めてから判定まで）/ `判定済み` | 段階が変わるたび | `計画中` |
| hypothesis | 何を変えると、どのプロンプトで、何が変わると考えるか。1文で | 変更前のラウンドの前 | `料金ページに税込の料金表を載せると、料金を尋ねるプロンプトで自社の引用が増える` |
| change_category | 変更の分類を1つ。`コンテンツ` / `エンティティ` / `クローラー` / `外部の言及` / `技術` | 変更前のラウンドの前 | `コンテンツ` |
| change_summary | 変える場所と中身を1行で | 変更前のラウンドの前 | `https://kakuu-coffee.example/pricing/ に税込の料金表と改定日を追加` |
| changed_on | 本番に反映した日。編集した日ではない | 反映したあと | `2026-10-15` |
| primary_metric | 確認的に判定する指標。`mention`（言及率）か `citation`（引用率） | 変更前のラウンドの前 | `citation` |
| primary_group | 確認的に判定する1組。service/surface/login/mode/region/language の順に `/` で区切る | 変更前のラウンドの前 | `chatgpt/web/なし/検索あり/JP/ja` |
| alpha | 符号検定の有意水準。既定は 0.05 | 変更前のラウンドの前 | `0.05` |
| min_effect | 実務上の最小効果（プロンプトごとの率の差の平均）。空なら使わない | 変更前のラウンドの前 | `0.10` |
| entities_sha256 | 固めた時点の entities.csv の SHA-256。`observations.run.json` の entities_sha256 の値をそのまま写す | entities.csv を固めたあと、1回目の変更前のラウンドを始める前（手順4）。変更前のラウンドを貼り終えたら、同じ値かを確かめる | （observations.run.json の値） |
| target_prompts | 対象プロンプトの ID。`,` で区切る | 変更前のラウンドの前 | `P003, P007, P008, P011, P012, P015, P018, P021, P022, P024` |
| control_prompts | 対照プロンプトの ID。なければ空 | 変更前のラウンドの前 | `P001, P005, P009, P010, P013, P014` |
| baseline_rounds | 変更前のラウンド名。2つ以上 | 変更前のラウンドの前 | `2026-10-01, 2026-10-08` |
| after_rounds | 確認的な判定に使う変更後のラウンド名。baseline_rounds と同じ数にする | 変更前のラウンドの前（日付は予定） | `2026-10-29, 2026-11-12` |
| verdict | 報告の「確認的な判定」をそのまま写す | 判定したあと | `改善シグナル` |

決め方の要点:

- primary_metric: 自社のページを直す施策（コンテンツ、技術）は、自社の URL が出典に出るかを見る `citation` が合う。社名の認知や外部での言及を増やす施策（エンティティ、外部の言及）は `mention` が合う。
- primary_group: 観測だけの運用で使っている組から1つ選ぶ。値は回答ファイルの欄と同じ表記にする（`compare_runs.py --period` の報告の組の見出しと同じ値を、同じ順に並べる）。mode の値に `/` を入れない。new_round.py の `--mode` も `/` を受け付けない。モデル名を足すなら `検索あり・Think` のように `・` でつなぐ（[03-observation.md](03-observation.md)）。手で書いた mode に `/` が入っていても、compare_runs.py は前から3つと後ろから2つを除いた残りを mode として読む。region と language には `/` を入れない。
- primary_group が観測したどの組とも一致しないと、確認的な判定は判定不能になり、報告の警告に観測した組の一覧が出る（手順8）。
- 検索を使うモードを選ぶ。検索を使わないモードの回答は、モデルがすでに学んだ内容から作られる（推定）ので、ページの変更が実験の期間内に届くとは考えにくい。
- Google の AI による概要（`google-aio`）は、表示されない回答（status が `AI の回答なし`）が分母から外れる。前後で有効な回答の数がそろいにくく、比較から外れるプロンプトが増えやすいので、primary_group には向かないことがある。
- min_effect: これより小さい変化なら手間に見合わない、と考える大きさにする。例（架空）: 前後6件ずつ比べるとき、1問で1件増えれば差は +0.167。10問のうち6問で1件ずつ増え、残りが同じなら差の平均は +0.100 になる。
- alpha を小さくすると、同じ件数ではシグナルが出にくくなる。変えるなら手順1の表を計算し直して、対象の数が足りるかを確かめる。

本文には、仮説の根拠、変更の中身（変更前と変更後）、対象と対照を選んだ理由を書く。欄の値と本文の書き方は `templates/experiment.md` にある。

### 手順3 対象プロンプトと対照プロンプトを選ぶ

対象プロンプトは、変更したページや情報が答えになりうるプロンプト。対照プロンプトは、変更の影響を受けにくいが、サービス側の変動（モデルの更新、検索の仕組みの変更、季節や報道による回答の変化）は同じように受けるプロンプト。対象の差から対照の差を引けば、サービス側の変動をある程度まで取り除ける。

対象の選び方:

- 変更前の率に動く余地があるものを選ぶ。毎回引用されている（率が 1 の）プロンプトは上がりようがない。一度も引用されない（率が 0 の）プロンプトは、変更が届かなければ前後とも 0 のままで、m に入らない。
- intent_group を散らす（手順1）。
- 変更前の率は、観測だけの運用で記録した直近のラウンドから取る。これから記録する変更前のラウンドの結果を見て選び直さない。

対照の選び方（対象となるべくそろえる）:

| そろえるもの | 理由 |
|---|---|
| 段階（stage）と、意図の近さ | 比較・購入の質問と認知の質問では、回答の作られ方や引用される情報源が違うことがある |
| 指名・非指名（branded） | 社名を含む質問と含まない質問では、自社が回答に出る理由が違い、動き方も違いうる |
| 変更前の率 | 率が 0 や 1 に張り付いた対照は、片方の向きにしか動けない |
| サービスと観測の条件 | 同じ組で観測したものだけが対照になる。compare_runs.py も組ごとに分けて集計する |

- 変更が届きうるプロンプトを対照に入れない。例（架空）: 料金ページを直す実験で、段階が違うからと「架空珈琲とサンプル焙煎の定期便はどちらが安いですか」を対照にすると、同じ料金ページが引用されて対照も動く。
- 会社の基本情報を直す（エンティティ）実験では、社名を含むプロンプトのほとんどに変更が届きうるので、よい対照を作りにくい。使える対照が1つもなければ（対照を置かないときと、対照のどのプロンプトも前後の比較の条件を満たさないとき）、対象がシグナル（改善シグナルか悪化シグナル）のときだけ、判定の理由に「対照がないため、サービス側の変動と区別できない」と書かれる。そのまま受け止める。
- 同じプロンプトを対象と対照の両方に入れない。
- 言い回しを直したプロンプトは別の ID になる（[02-prompt-set.md](02-prompt-set.md)）。実験の途中で prompts.csv の文を直さない。

### 手順4 変更前のラウンドを記録する

- 変更前のラウンドは2回以上にする。観測の条件のそろえ方、新しい会話で尋ねること、2日以上に分けることは [03-observation.md](03-observation.md) に従う。
- 実験だけのために尋ねるなら、対象と対照のプロンプトに絞ってひな形を作れる（例は架空の ID）。`--mode` には primary_group の mode と同じ値を付ける。全ファイルの mode の欄にその値が入る。

```bash
python3 <スキルのディレクトリ>/scripts/new_round.py --round 2026-10-01 --services chatgpt --repeats 3 --mode 検索あり \
  --prompts P001,P003,P005,P007,P008,P009,P010,P011,P012,P013,P014,P015,P018,P021,P022,P024
```

1回目の変更前のラウンドで AI に尋ね始める前に、entities.csv を固め、その版を実験の記録に残す。

1. entities.csv の表記ゆれ・除外語・ドメインに漏れがないかを、[01-setup.md](01-setup.md) に照らして見直す。ここから判定が済むまで、この一覧は変えない（手順5）。
2. normalize_observations.py を実行し、`ai-search/observations.run.json` の entities_sha256 を実験の記録に写す。ひな形を作ったあとなら、回答を貼る前でも実行できる。まだ貼っていない回答は `未記入` として扱われ、率には入らない。
3. status を `実施中` にする。

```bash
python3 <スキルのディレクトリ>/scripts/normalize_observations.py --workspace ai-search
```

- `--mode` を付けずにひな形を作ったときは、mode の欄が空になる。回答を貼るときに、毎回 primary_group の mode と同じ表記で書く。表記が違うと別の組として集計され、primary_group から外れる。変更後のラウンドのひな形も、変更前と同じ `--mode` の値で作る。
- 記録できなかった回答（エラー、回答拒否など）は status に書く。空のまま残すと「言及なし」と区別できなくなる。
- 変更前のラウンドをすべて貼ったら、normalize_observations.py をもう一度実行する。observations.run.json の entities_sha256 が実験の記録の値と同じかを確かめる。違えば、変更前のラウンドの途中で entities.csv が変わっている。記録の値は書き換えず、変えた日と理由を本文の「期間中に起きたこと」に書く。判定の報告にも警告が出る。
- 任意: 変更前の2つのラウンドどうしを比べると、何も変えていないのにどれだけ揺れるかがわかる。ここでシグナルが出るなら、そのサービスは揺れが大きいので、変更後の判定も慎重に読む。この比較は探索的なもので、実験の判定には使わない。

```bash
python3 <スキルのディレクトリ>/scripts/compare_runs.py --before 2026-10-01 --after 2026-10-08 \
  --targets P003,P007,P008,P011,P012,P015,P018,P021,P022,P024 --controls P001,P005,P009,P010,P013,P014 \
  --metric citation
```

### 手順5 変更を本番に反映し、反映日を書く

- 反映したら、公開された URL をブラウザで開いて中身を確かめ、その日を changed_on に書く。本文の「変更の中身」に、変更前と変更後の文や表を残す。
- ページの書き直し、構造化データ、内部リンクの作業そのものは seo-operator の 06-writing-editing.md・07-on-page.md・08-internal-linking.md に任せる。seo-operator がなければ、対象 URL・足りないもの・根拠（どのプロンプトのどの回答か）を箇条書きで渡す。
- 1回の実験で変えるのは1つの分類だけにする。判定が済むまで、同じページ、および対象プロンプトの答えになりうるほかのページに、別の変更を入れない。どの変更が効いたか切り分けられなくなる。
- 実験の途中で entities.csv を変えない。表記ゆれの漏れに気づくなどして変える必要が出たら、変えた日と理由を本文の「期間中に起きたこと」に書く。normalize_observations.py は過去のラウンドも新しい一覧で判定し直すので、報告に entities_sha256 の違いの警告が出る。
- prompts.csv は、既存の行の prompt・stage・branded・intent_group を変えず、行も消さない。prompt を直すと前後で別の質問になり、ほかの3つを変えると過去のラウンドの内訳も変わる。対象と対照の行の active も `no` にしない（`--prompts` を付けずに new_round.py を実行すると、その行のひな形が作られない）。新しい行を足すのはよい。足した問いは片方の期間にしかないので、この実験の判定には入らない（[02-prompt-set.md](02-prompt-set.md)）。

### 手順6 変更後のラウンドを記録する

変更が AI の回答に届くまでの期間は、決め打ちできない。2026-09-26 に公式資料で確かめた範囲は次のとおり。

- Google: AI による概要・AI モードにリンクが出るには、ページがインデックスに登録され、スニペットを表示できる必要がある。プレビュー コントロールのトラブルシューティングの節には、ページの更新頻度の判断に応じて、クロールに「数日から数か月かかる場合があります」とある（[AI 機能とウェブサイト](https://developers.google.com/search/docs/appearance/ai-features?hl=ja)、日本語版の最終更新日 2025-12-31。英語版は 2025-12-10）。再クロールのリクエストの説明では「数日から数週間」とある（[Google に再クロールをリクエストする](https://developers.google.com/search/docs/crawling-indexing/ask-google-to-recrawl?hl=ja)、日本語版の最終更新日 2025-12-31）。
- Google の生成 AI 機能向けの最適化ガイド: 変更が表示に反映されるまでの期間は書かれていない（[Google 検索の生成 AI 機能向けにウェブサイトを最適化する](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide?hl=ja)、日本語版の最終更新日 2026-09-23。英語版は 2026-07-10）。
- OpenAI: 検索結果（OAI-SearchBot の設定）については、robots.txt を更新してから OpenAI のシステムが対応するまで約24時間かかることがある、とある（[Overview of OpenAI Crawlers](https://developers.openai.com/api/docs/bots)）。学習用の GPTBot には、期間の記述がない。OAI-SearchBot の許可・拒否を変える実験の目安にはなるが、GPTBot の実験には当てはまらない。ページの内容の変更が回答に届くまでの期間でもない。
- Claude、Gemini、Copilot: ページの変更が回答に届くまでの期間を書いた公式資料は、確認できていない。

このため、次のように進める。

- after_rounds は、変更前のラウンドを始める前に決めた日付で記録する。変更後のラウンドは、反映日から同じ間隔で置く（たとえば2週間ごと）。反映の直後だけで測ると、変更がまだ届いていないことがある。
- 変更後のラウンドは、変更前と同じ数のラウンド、同じ繰り返しの回数、同じ観測の日数にする。1プロンプトあたりの有効な回答の数が前後で違うと、そのプロンプトは比較から外れる。
- changed_on より前の日に after のラウンドを始めない（報告に警告が出る）。
- 確認的な判定のあとも、同じ間隔で観測を続けてよい。そこから先の比較は探索的なものとして扱う（手順9）。

### 手順7 判定する

変更後のラウンドをすべて貼ったら、観測ログを作り直してから判定する。コマンドは作業フォルダ（`ai-search/` がある場所）で実行する。

```bash
python3 <スキルのディレクトリ>/scripts/normalize_observations.py --workspace ai-search
python3 <スキルのディレクトリ>/scripts/compare_runs.py --experiment ai-search/experiments/E001.md \
  -o ai-search/reports/E001-report.md --details-csv ai-search/reports/E001-details.csv
```

- `--experiment` は、実験の記録から対象・対照・ラウンド・primary_metric・primary_group・alpha・min_effect を読む。確認的な判定を出すときは、`--metric` で primary_metric を外しても、primary_metric が判定に加わる。
- 次のどれかに当たると、報告は確認的な判定を出さず、すべて探索的な比較として扱う。報告の「## 結論」の最初の行が「確認的な判定: 出さない（理由）。すべて探索的な比較として扱う。」になり、「確認的な判定（組、指標）」の行は出ない。
  - `--before`・`--after`・`--targets`・`--controls`・`--alpha`・`--min-effect` に、記録と違う値を指定した。変えた内容は、報告の冒頭の条件の箇条書きに書かれる
  - 記録の空の欄（after_rounds、control_prompts、min_effect など）を、これらのオプションで補った
  - `--min-repeats` を既定の 3 から変えた。実験の記録にはこの欄がないので、既定の値を事前に決めた条件とみなす
  - `--group-by` を既定から変えた。primary_group と組が対応しなくなる
  - 実験の記録に primary_group か primary_metric がない。または target_prompts が空（`--targets` で補っても出ない）
- 記録と同じ値をオプションで指定しても、確認的な判定には影響しない。プロンプトやラウンドの一覧は、並び順が違うだけなら同じ値とみなす。
- 条件を変えた比較の結果は、探索的な結果として本文に書く。実験の判定は、記録の条件のまま実行した報告の「確認的な判定」から取る。
- `--details-csv` は、プロンプトごとの比較表（group、metric、set（target / control）、prompt_id、before_k、before_n、after_k、after_n、diff、status）を書く。status は、比べたプロンプトなら `比較した`、外したプロンプトなら外した理由になる。
- 実行すると、標準エラー出力に「比較しました: 組 ○ 件、判定 ○ 件（確認的な判定: 判定）」の要約が出る。確認的な判定を出さないときは、括弧の中が「すべて探索的」になる。primary_group の組が判定の表にないときは、「確認的な判定: 判定不能（primary_group の組が見つからない）」のように短い理由が付く（手順8の「判定不能になる主な理由」）。
- 終了コードが 2 なら、入力か引数の誤り。標準エラー出力の日本語のメッセージ（observations.csv がない、指定したラウンドが observations.csv にない、同じラウンドが変更前と変更後の両方にある、など）に従って直す。指定したラウンドのうち1つでも observations.csv になければ、報告を出さずに止まる。

### 手順8 報告を読む

報告は、「# AI 検索の前後比較」、条件の箇条書き、「## 結論」、「## 組ごとの判定」（組ごとに「### 組」の見出しと表）、「## 外したプロンプト」、「## 比較できない組」（あるときだけ）、「## 有効な回答がない組」（あるときだけ）、「## 警告」、「## 注記」の順に並ぶ。

- 「## 比較できない組」: 片方の期間にしか有効な回答がない組。実験に使わなかったサービスの組（変更後のラウンドを一部のサービスだけで作ったときなど）がここに入る。判定の表と「探索的な判定の内訳」には入らない。組ごとに、有効な回答の件数と AI の回答の表示率が前後で添えられる。条件の箇条書きに「比較できない組: ○」の行が、「## 警告」に組ごとの行（1組につき1行）が出る。
- 「## 有効な回答がない組」: 前後どちらの期間も、未記入のひな形・エラー・回答拒否などの回答だけの組。判定の表にも集計の表にも入らない。

「## 結論」は、条件の箇条書きのすぐ後ろにある。primary_group × primary_metric の判定が「確認的な判定（組、指標）: 判定。理由」の1行で書かれる。実験の判定として記録するのは、この1行だけ。確認的な判定を出さない場合（手順7）は、この1行が「確認的な判定: 出さない（理由）。すべて探索的な比較として扱う。」になる。この報告からは、実験の判定を記録しない。

報告の数値の意味:

| 報告の欄 | 意味 | 読み方 |
|---|---|---|
| 前・後 | 期間ごとの件数 k/n（自社の言及か引用があった有効な回答 / 有効な回答）。対象のプロンプトの回答すべてを数える | 規模の確認に使う。判定はこの合計ではなく、プロンプトごとの差で行う |
| 比較した・外した | 前後で有効な回答の数が同じで、`--min-repeats`（既定 3）件以上あるプロンプトの数 / それ以外の数 | 外したプロンプトが多いと m が減る。外した理由を「## 外したプロンプト」で確かめる。理由は「片方の期間にしかない」「前後で有効な回答の数が違う（前 ○ 件、後 ○ 件）」「有効な回答が 3 件未満（○ 件）」「この組で観測がない」のどれか。3 は `--min-repeats` の値 |
| 上がった・下がった・同じ | プロンプトごとの差 d（後の率 − 前の率）の向き | 同じは m に入らない |
| 差の平均 | 比較したプロンプトの d の平均。1問ずつ同じ重みで数える | 変化の大きさの目安。+0.100 は率で10ポイント上がったことを表す |
| 差の中央値 | d を小さい順に並べた真ん中の値 | 平均と大きく違えば、少数のプロンプトが平均を動かしている |
| m | 上がった件数と下がった件数の合計 | 6未満なら判定不能 |
| p | 両側の正確な符号検定の p 値。小数第3位まで出し、丸めると α と同じに見えるときは違いが見えるまで桁を増やす（α 0.05 に対して 0.0498 など） | 向きがそろっているかの確認。α 未満なら「そろっている」とみなす。変化の大きさも原因も示さない |
| 対照の差の平均 | 対照プロンプトの d の平均 | サービス側の変動の目安 |
| 調整した差 | 対照で調整した差（対象の差の平均 − 対照の差の平均） | シグナルと同じ向きなら、シグナルのまま（min_effect があれば、その大きさ以上のときだけ） |
| 判定・理由 | 4つの判定のどれかと、その理由 | 「（確認的）」が付いた行が確認的な判定。「（探索的）」が付いた行は確認的な判定ではない |

4つの判定の意味:

| 判定 | 出る条件 | 言えること | 言えないこと |
|---|---|---|---|
| 改善シグナル | m が6以上、p < α で上がったほうが多い。min_effect があれば差の平均がそれ以上。対照があれば、対照で調整した差も同じ向きで min_effect 以上 | 施策と整合的な変化が見えた | 施策が原因であること。今後も続くこと。ほかのサービスでも起きること |
| 悪化シグナル | 上と同じ条件で、下がったほうが多い | 施策と整合的な悪化が見えた | 施策が原因であること |
| 明確な変化を検出せず | m は6以上だが向きがそろっていない（p ≥ α）。または p < α でも、差の平均が min_effect に届かない | この件数と基準では、はっきりした変化が見えなかった | 変化がなかったこと。施策が効かないこと |
| 判定不能 | m が6未満。または対象はシグナルだが、対照も同じ程度に動いた（調整した差が逆向き、ゼロ、または min_effect に届かない）。または primary_group の組が判定の表にない（観測したどの組とも一致しない、片方の期間にしか有効な回答がない、どちらの期間にも有効な回答がない）。または primary_group に一致する組が表記ゆれで割れている（下の「判定不能になる主な理由」） | この条件では判定できない | 効果があったこと、なかったこと |

改善シグナルは、施策と整合的な変化が見えたという意味で、原因を示すものではない。同じ時期のモデルの更新、競合のページの変化、報道、同じサイトのほかの変更でも同じ動きは起きる。対照で差し引けるのは、対照にも同じように届いた変動だけである。

「明確な変化を検出せず」は、変化がないという意味ではない。対象が少ない、向きの違うプロンプトが混ざった、効果が min_effect より小さかった、のどれでも同じ判定になる。例（架空）: 9問で差が出て、5問が上がり4問が下がれば、p = 1.000 でこの判定になる。上がった5問だけを見れば大きく動いていても、下がった4問と打ち消し合う。

判定不能になる主な理由:

- 差が出たプロンプトが少ない（m が6未満）。対象が少ない、率が 0 や 1 のまま動かないプロンプトが多い、記録できなかった回答で前後の件数がずれて比較から外れた、のどれか。外したプロンプトの一覧と `--details-csv` で、どれに当たるかを確かめる。
- 対照も同じ程度に動いた。サービス側の変動の可能性がある。変更が対照にも届いた（対照の選び方の失敗）可能性もあるので、手順3に照らして確かめる。
- primary_group の組が判定の表にない。「## 結論」の確認的な判定の行は、理由によって次の3つのどれかになる。表記の誤りを直すなら、直した理由を本文に書く。別の組に選び直さない。
  - 「判定不能。primary_group の組が、指定したラウンドの観測にない（書き誤りの可能性。観測した組は「警告」を参照）」: primary_group が、観測したどの組の有効な回答とも一致しない。表記（特に mode）が回答ファイルの値と違う可能性がある。「## 警告」に観測した組の一覧（10組まで）が出るので、primary_group と見比べる。
  - 「判定不能。変更後の期間にこの組の有効な回答がない（「比較できない組」を参照）」: この組の有効な回答が、片方の期間にしかない。変更前の期間にないときは「変更前の期間に…」になる。その期間にこの組を観測していないか、回答がすべてエラーなどで記録できなかった。
  - 「判定不能。この組の有効な回答が、指定したラウンドにない（「有効な回答がない組」を参照）」: この組の回答はあるが、前後どちらの期間も未記入のひな形・エラー・回答拒否などだけ。回答の貼り忘れと status を確かめる。
- primary_group に一致する組が表記ゆれで割れている。primary_group と表記が完全に一致する組があれば、その組で判定する。完全に一致する組がなく、大文字・小文字や全角・半角だけが違う組（`JP` と `jp` など）が2つ以上一致すると、確認的な判定の行は「判定不能。primary_group に一致する組が表記ゆれで n つに割れている（…）」になる。回答ファイルの表記をそろえて normalize_observations.py を実行し直し、直したことを本文に書く。

数値の読み方の例（架空）: 手順2の例の E001 で、報告が次のようになったとする。

- 比較から外したもの: 対象10問のうち P024。変更後の期間に1件がエラーになり、有効な回答が前6件・後5件とそろわなかった。
- m と p: 比較した9問は、上がった8・下がった0・同じ1。m = 8、p = 0.008 で、α = 0.05 を下回る。
- 差の平均・中央値: 差の平均は +0.259、中央値は +0.333。差の平均が min_effect の 0.10 以上。
- 対照の差と調整した差: 対照6問の差の平均は +0.028。対照で調整した差は +0.231。向きが同じで、min_effect 以上。
- 確認的な判定: 改善シグナル（対照で調整しても同じ向き）。

報告に書けるのは「料金ページに料金表を載せたあと、ChatGPT の検索ありの回答で、料金を尋ねる質問に自社の URL が出典として出る回答が増え、施策と整合的だった」まで。「料金表のおかげで引用が増えた」とは書かない。

確認的な判定と探索的な判定:

- 確認的な判定は、実験の記録に書いた primary_group × primary_metric の1つだけ。
- ほかの組、ほかの指標、stage 別・指名・非指名別の結果、実験の記録なしの比較、条件をオプションで変えた比較は、すべて探索的な判定になる。次の実験の仮説を作る材料には使えるが、結論にはしない。
- 比べる組と指標を増やすほど、偶然の差がシグナルに見えやすくなる。多重比較の補正（Holm 法など）は v1.0.0 では行わず、確認的な判定を1つに絞ることで扱っている。

報告の警告と対応:

| 警告 | 何が起きているか | 対応 |
|---|---|---|
| 前と後で観測した日数が違う、ある期間の回答がすべて同じ日、observed_at に日付がない有効な回答がある | 日による回答の揺れが、前後で違う形で入っている。日付がない回答は、日数の確認から外れている | 判定は警告付きのまま記録する。日付の書き漏れなら observed_at を書いて normalize_observations.py を実行し直す。次の実験では 03 の決まり（2日以上に分け、前後で日数をそろえる）に従う |
| 前と後でモードの種類が違う | 観測の条件が変わったか、mode の表記が揺れている | 表記の揺れなら、回答ファイルの mode を直して normalize_observations.py を実行し直し、直したことを本文に書く |
| この組は有効な回答が前（または後）の期間にしかない（比較できない。「比較できない組」を参照） | もう片方の期間にこの組を観測していないか、その期間の回答がすべて記録できなかった。1組につき1行出る | 実験に使わなかったサービスの組なら、そのままでよい。primary_group の組なら、確認的な判定は判定不能になる（上の「判定不能になる主な理由」）。mode の表記の揺れで組が分かれたなら、上の行と同じく mode を直す |
| 実験の記録の primary_group に一致する組が、指定したラウンドの有効な回答にない | primary_group の書き誤りか、その組を観測していない。警告の末尾に、観測した組が10組まで並ぶ | primary_group と観測した組を見比べる。書き誤りなら直し、直した理由を本文に書く。別の組に選び直さない |
| 表記（大文字・小文字、全角・半角など）だけが違う組が n つに分かれている。実験の記録の primary_group に、表記だけが違う別々の組が n つ一致する | region・language・mode などの表記が回答ファイルによって揺れ、同じ条件の回答が別々の組に分かれた。組は書いたとおりの値で分け、合算しない | 回答ファイルの表記をそろえて normalize_observations.py を実行し直し、直したことを本文に書く。primary_group の組が割れたままなら、確認的な判定は判定不能になる |
| 片方の期間にしかないプロンプト、前後で有効な回答の数が違うプロンプト | そのプロンプトは比較から外れている | 外した数が多ければ、判定不能の理由として記録する |
| 対象（または対照）のプロンプトのうち、指定したラウンドのどの回答にもない ID | ID の打ち間違いか、そのプロンプトを尋ねていない | 実験の記録の ID を prompts.csv と見比べる。打ち間違いなら直し、直した理由を本文に書く |
| changed_on より前の日の回答がある変更後のラウンド、changed_on より後の日の回答がある変更前のラウンド | ラウンド名か反映日の書き誤り、または反映の前に観測した | 書き誤りなら直し、直した理由を本文に書く。実際に反映前に観測したラウンドは after_rounds に入れない |
| changed_on と同じ日の回答がある（反映の前か後か区別できない） | 反映した日に観測した | 反映の時刻がわかれば observed_at の時刻と比べ、どちらが先だったかを本文に書く。わからなければ、区別できないと書く。次の実験では、反映した日に観測しない |
| 実験の記録に changed_on がない | 反映日を書いていない | 反映日を確かめて changed_on に書き、判定し直す |
| 実験の記録の entities_sha256 と observations.run.json の値が違う | 実験の記録に値を写したあとで entities.csv を変えた | 変えた理由を本文に書き、警告を消さずに報告に残す |
| 実験の記録に entities_sha256 がない、形式が不正、observations.run.json がない（または entities_sha256 がない） | entities.csv を途中で変えたかを確かめられない | observations.run.json がなければ normalize_observations.py を実行する。記録の値は手順4で写すもので、判定のときに今の値を写しても、途中で変えていないことの確認にはならない。確かめられなかったことを本文に書く |

誤った説明の率（error）と AI の回答の表示率は、前後の判定をしない。報告の件数の表を、判定とは別に並べて読む。

### 手順9 記録を閉じる

- 報告の「確認的な判定」を verdict に写し、status を `判定済み` にする。本文の「結果」に報告のファイル名、数値、警告を書き、「考察」に言えることと言えないことを分けて書く。
- どの判定でも記録を残す。明確な変化を検出せず・判定不能の実験を消すと、うまくいった実験だけが残り、施策の効き方を実際より大きく見積もる。
- 次の一手は判定ごとに決める。
  - 改善シグナル: 同じ種類の変更をほかのページに広げるなら、新しい実験として記録する。ほかのサービスでも見たいなら、そのサービスを primary_group にした別の実験にする。
  - 悪化シグナル: 変更を戻すかどうかは、事業への影響（brief.md の目標）と合わせてユーザーが決める。戻すなら、戻した日を記録し、戻したあとの観測も同じ組で続ける。
  - 明確な変化を検出せず: 施策が効かないと決めつけない。別の分類の施策を試すか、対象プロンプトを増やした実験を設計し直す。
  - 判定不能: 理由（手順8）に応じて、対象を増やす、繰り返しやラウンドを増やす、対照を選び直す、のどれかで次の実験を設計する。
- 判定不能だったあとに after のラウンドを足して判定し直すと、前後のラウンドの数がそろわず、ほとんどのプロンプトが比較から外れる。ラウンドを入れ替えて同じ数で比べ直すのは可能だが、その結果は探索的な判定になる。
- 確認的な判定のあとに続けた観測で変化が見えても、確認的な判定は書き換えない。本文に探索的な結果として追記する。

## 6. よくある失敗

- 結果を見てから primary_metric や primary_group を選ぶ: シグナルが出た組と指標を後から選ぶと、偶然の差を拾う。変更前のラウンドの前に決め、実験の記録に書いたものだけを確認的な判定にする。
- 変更後のラウンドのたびに判定し、シグナルが出たところで止める: 何度も見るほど偶然のシグナルに当たりやすい。確認的な判定に使う after_rounds は先に決め、それ以降の観測は探索的に扱う。
- 改善シグナルを「施策の効果」と報告する: シグナルは施策と整合的な変化が見えたという意味にとどまる。同じ時期の出来事を「期間中に起きたこと」に書き、原因は断定しない。
- 「明確な変化を検出せず」を「効果なし」と書く: 件数が少ない、向きが混ざった、効果が小さかった、のどれでも同じ判定になる。変化がなかったとは言えない。
- 判定不能を失敗として記録から消す: 明確な変化を検出せず・判定不能の実験も残す。消すと、うまくいった実験だけが残る。
- 1回の実験で料金表・構造化データ・内部リンクをまとめて変える: どれが効いたか切り分けられない。1回の実験で変えるのは1つの分類だけにする。
- 前と後でラウンドの数や繰り返しの回数が違う: プロンプトごとの有効な回答の数がそろわず、ほとんどが比較から外れて判定不能になる。
- 対照に、変更が届きうるプロンプトを選ぶ: 対照も一緒に動き、対照で調整した差が小さくなって判定不能になる。対照は変更の影響を受けにくいものから選ぶ。
- 記録できなかった回答を空のまま残す: 「言及なし」と区別できない。status に `AI の回答なし`・`回答拒否`・`エラー` を書く。
- 実験の途中で entities.csv の表記ゆれを足し、黙って判定する: 過去のラウンドの判定も変わる。変えた日と理由を記録し、報告の警告を消さない。
- 検索を使わないモードで、ページを直す施策を判定する: ページの変更が回答に届く経路が見込めない。確認的に判定する組は、検索を使うモードから選ぶ。
- 効果が出るまでの期間を「2週間」などと決め打ちして説明する: 変更が AI の回答に届くまでの期間を示した公式資料は、確かめた範囲では見つかっていない（手順6）。同じ間隔で測り、観測した結果だけを報告する。
